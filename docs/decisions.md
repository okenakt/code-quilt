# 検討経緯

設計判断ごとに、結論、そこに至った経緯、採用しなかった案を記録する。実装中に「不採用案の方が簡単では？」となったときは、まずここを確認する。

## 1. セッションの掴み方：cqラップ方式

**結論**：シェルのエイリアスで `claude` を `cq claude` に差し替え、cq hostがclaudeのPTYを保持する。

**経緯**：当初はAgent SDKなどの構造化プロトコルを主軸に考えた。しかし、手元で普通に起動したセッションを後から取り込むことが必須となり、方針を変えた。次に、claude側に手を入れずターミナルも選ばないChannelsを検討した。最終的に、claudeとcodexで違うやり方にしたくないという方針からcqラップを選んだ。

**採用しなかった案**

- Agent SDK主軸：オーケストレーターから起動する前提で、既存の対話型セッションを取り込めない。
- Channels：Claude専用でCodexに相当機能がない。入力が外部メッセージ扱いで、中断やスラッシュコマンドを送れない。リサーチプレビューで、開発フラグと組織設定に依存する。

**代償**：二重ConPTYによるキー互換性（Shift+Enter、ペースト、日本語IMEなど）のリスクを自前で引き受ける。M0で最初に検証する。

## 2. Codexとの共通化の範囲

**結論**：入出力を担う共通層（cq host）と、状態・履歴の取得を担うAdapter層に分ける。

**経緯**：PTYラップによって、入出力と表示はエージェントに依存せず共通化できる。一方、「人間待ち」の判定を画面から行うのは脆いため、Claudeはhooks、Codexはnotifyとセッションログ、というようにエージェントごとの情報源が必要になる。違いが出る部分をAdapterに閉じ込めた。状態モデルは当面Claudeベースで作り、Codex追加時に合わせ方を再検討する。

## 3. セッションの寿命：セッションごとのcq host

**結論**：dtach型で、セッションごとに独立したcq hostプロセスがPTYを保持する。

**経緯**：ハブは未起動だったり、落ちたりすることが前提である。1つのデーモンが全セッションを保持すると、その障害で全滅する。セッション単位でプロセスを分ければ、ハブやdaemonがどうなってもセッションは残る。

## 4. 接続の向き：待ち受け型

**結論**：cq hostとdaemonが待ち受け、クライアントから接続しに行く。

**経緯**：daemonからハブへ外向きに接続する方式はNAT越えに強いが、ハブ不在の間、再接続を繰り返すことになる。ハブ非依存という前提には待ち受け型が素直である。

## 5. リモート接続：sshのstdio方式

**結論**：クライアントが `ssh <host> cq bridge` を実行し、その標準入出力を通信路にする。

**経緯**：sshのポートフォワード、Tailscale上でのWebSocket直接接続、stdio方式を比較した。stdio方式はVS Code Remote SSHと同じやり方で、リモート側にポートを開けずに済み、既存のssh鍵認証をそのまま使える。追加の認証の仕組みを作る必要もない。

## 6. マシンの発見：事前登録

**結論**：監視するマシンは、`~/.ssh/config` のホストから選んで事前に登録する。

**経緯**：Claudeのリモートコントロールは、Anthropicのサーバーがアカウント単位でセッションを管理するため、どこで起動しても自動で見える。CodeQuiltは中央サーバーを持たないので、接続先をクライアント側で知っている必要がある。個人利用の規模では中央サーバーは過剰なので、登録の手間を最小化する方向にした。マシンが増えたら、軽量なレジストリを後付けできる構造にしておく。

## 7. 承認の返し方：通知はhook、回答はキー入力

**結論**：Notification hookで承認待ちを検出し、回答はcq hostが画面を確認したうえでキー入力として送る。

**経緯**：当初はPermissionRequest hookでハブの回答を返す案を考えた。しかし、hookが回答を待つ間はローカルのTUIに承認プロンプトが出ず、手元で答えられなくなる。これは「ローカルと同じ体験」と矛盾する。hookは通知だけにしてすぐ返し、ローカルとダイアログの先着を採用する形にした。

## 8. 承認のUI：独立ダイアログ

**結論**：承認は、どのセッションの要求かを明示した独立ダイアログで扱う。

**経緯**：オーケストレーターが推定して仲介すると、誤配送で別セッションの操作を承認する事故が起こりうる。承認は確実性を最優先し、ルーティングの仕組みから切り離した。

## 9. 状態の取得と設定の注入

**結論**：hooksとstatusLineを、起動時に `--settings ~/.codequilt/claude.json` で注入する。`~/.claude` 配下は書き換えない。

**経緯**：cqが介入した設定をclaudeに読ませることへの懸念から、注入なしの構成も検討した。トランスクリプトの監視と画面検出で大半は代替できるが、レート制限はstatusLineでしか取得できない。hooksが標準出力に何も書かなければトークン消費は増えないことを確認したうえで、起動時注入を採用した。statusLineはユーザー自身の設定に連鎖させ、ローカルの見た目を変えない。

**採用しなかった案**

- `~/.claude/settings.json` の書き換え：claude側の設定を汚す。
- 注入なし：レート制限が表示できない。
- 非公開の利用状況APIの直接呼び出し：非公開で、規約上もグレー。

## 10. レート制限の集約：アカウントID単位

**結論**：レート制限はマシンではなくアカウントIDで集約し、アカウントごとに1行表示する。

**経緯**：当初は全セッションが同一アカウントという前提だった。次に「1マシン1アカウント」としてマシンごとに表示する案になった。アカウントIDで集約すれば、その前提自体が不要になり、同一アカウントの複数マシン利用や、設定ディレクトリを分けた運用も自然に扱える。

## 11. オーケストレーターのカードと要約

**結論**：ターン終了ごとにカードを作り、そのカードをそのままルーティングの判断材料にする。ユーザーはすべてのカードに答える必要はない。

**経緯**：当初、要約は「ルーティングの判断材料」として想定していた。一方で、レスポンスごとに要約してユーザーに提示するというイメージもあり、両者を同じものに統一した。答えなかったカードが何もブロックしないように状態を持たせ、カードへの返信も宛先指定の手段に加えた。

## 12. オーケストレーターのLLM：ローカルのclaude -p

**結論**：要約とルーティングには、ローカルの `claude -p` を使う。

**経緯**：Claude APIを直接呼ぶ案もあったが、サブスクリプション内で完結する方を選んだ。代わりに同じアカウントの5h枠を消費するので、短い応答は要約せず、オーケストレーター自身の消費も可視化する。

## 13. 実装言語：Rust

**結論**：cq・cq host・daemonなどバックエンドとツール群はすべてRustで書く。

**経緯**：stdio方式ではリモートに `cq` を置く必要があり、依存のない単一バイナリが望ましい。cq hostはセッションごとに1プロセスなので、軽さも効く。portable-ptyやinterprocessでOS差を吸収でき、Ubuntu対応の差分が小さい。プロトコルの型を全コンポーネントで共有できる。弱点はUI開発の速さで、Node / TypeScriptに劣る。

## 14. UI：Tauri＋React

**結論**：UIはTauri＋React（dockview、xterm.js）で作る。

**経緯**：Rustのバックエンドと統合しやすい。ただし、UbuntuではWebKitGTKになり、xterm.jsの描画性能に不安がある。UIをdaemonとプロトコルで話すだけの構成にして、問題が出たらフロントエンドをElectronへ載せ替えられるようにしておく。

## 15. スコープから外したもの

- **自動承認ポリシー**：各エージェントのローカル設定の範囲であり、本プロジェクトでは扱わない。
- **Telegramブリッジ**：当面はOS通知で足りる。

## 16. 実装時の決定と仮決定（2026-10-02）

M0〜M4（音声入力を除く）の実装中に決めたこと。「仮」は未決事項を暫定値で埋めたもので、使ってみて見直す。

### 16.1 単一バイナリ `cq`

**結論**：cq host・daemonは別バイナリにせず、`cq host` / `cq daemon` / `cq bridge` / `cq hook` / `cq statusline` のサブコマンドにまとめた。

**経緯**：リモートに置くものを1ファイルにするため。設計図ではそれぞれcq host・daemonと呼ぶ。

### 16.2 IPC：interprocessではなくtokioのnamed pipe / unix socket

**結論**：`tokio::net::windows::named_pipe` とunix socketを薄くラップした。

**経緯**：DACLを現在ユーザーのみ（`D:P(A;;GA;;;<SID>)`）にする指定と、`PIPE_REJECT_REMOTE_CLIENTS` を直接書けるため。非同期処理との統合も素直。フレームの読み取りは `select!` 内でキャンセル安全でないため、専用タスクで読みチャネルで受け取る（`spawn_reader`）。

### 16.3 カーソル位置問い合わせはhostが答える

**結論**：hostが画面グリッドからCPR（`ESC[6n`）に応答し、クライアントへの出力からは要求を取り除く。

**経緯**：portable-ptyはConPTYを `PSEUDOCONSOLE_INHERIT_CURSOR` 付きで作るため、起動時のCPRに誰も答えないと出力が止まる。ハブから端末なしで起動したセッションでは答える端末がいない。他の問い合わせ（DA、kittyの `?u`、OSC 11など）は接続中の端末が答えるため、複数端末の同時接続時に応答が重複しうる（既知の制約）。

### 16.4 入力：VT入力モード＋Shift+EnterのCSI u変換

**結論**：attachはコンソールをVT入力モードにし、`ReadConsoleInputW` で読む。VTに変換済みの文字はそのまま流し、Shift/Ctrl/Altの状態を自前で追跡して、Shiftだけが押されたEnter（ブラケットペースト外）を `ESC[13;2u` に置き換える。xterm.jsのタイルでも同じシーケンスを送る。

**経緯**：
- WezTermはclaudeがkittyキーボードを有効にするとShift+Enterを自分でCSI uにするため素通しで通ったが、Windows Terminal / conhostではVT変換でShiftが失われ `\r` になる。素のclaudeもPowerShellではShift+Enterで改行できない。
- win32-input-modeで再エンコードする案も試したが、claudeはShift付きEnterを改行として扱わず、ペーストがキーイベント列になってブラケットペーストが失われたため削除した。
- VT入力モードでも `ReadConsoleInputW` なら修飾キー自体のレコードが届くことを確認し、この方式にした。cq越しのclaudeは素のclaudeよりShift+Enterが効く。
- 表示崩れはコンソール出力モードで `ENABLE_WRAP_AT_EOL_OUTPUT` を落としていたことが原因で、修正済み。

### 16.5 デタッチキー：Ctrl+\

**結論**：Ctrl+\でデタッチする。`0x1c` に加え、modifyOtherKeys形式の `ESC[27;5;92~` とkitty形式の `ESC[92;5u` も検出する。

**経緯**：claudeがmodifyOtherKeysを有効にするため、端末はCtrl+\を `0x1c` ではなく `ESC[27;5;92~` で送っていた（`CQ_TRACE=1` の入力トレースで判明）。

### 16.6 セッション一覧：SQLiteは後回し

**結論**：`~/.codequilt/sessions/<id>.json` をそのまま一覧と状態の永続化に使う。終了したセッションも残り、resumeできる。

**経緯**：一覧・resume・終了状態の保持はJSONで足りた。状態履歴の検索やトークンの長期集計が必要になった時点でSQLiteを入れる。

### 16.7 イベントの再送：hostのメモリとUIバックエンドのキャッシュ

**結論**：hostが直近200件のイベントと、statusLine・account・tokensの最新値を保持し、ハブやMonitorの接続時に再送する。UIバックエンドもキャッシュを持ち、フロントエンドの再読み込み時に `replay` で渡す。スプールは耐久的な記録として残す。

**経緯**：daemonを状態なしに保ったまま、daemonやハブの再起動で状態を失わないため。statusLineなどを履歴に積むとStopなど重要なイベントが押し出されるので、最新値だけを持つ。

### 16.8 Monitor接続

**結論**：daemonは稼働中の全セッションに、出力を受け取らないMonitor接続を張る。承認の回答と、タイルを開いていないセッションへの入力（オーケストレーター）はMonitor経由で送る。Monitorからの入力は入力権とPTYサイズを変えない。

**経緯**：イベントは全セッション分必要だが、画面出力まで全部受けるのは無駄。オーケストレーターの貼り付けで手元ターミナルのサイズが変わるのも避けたい。

### 16.9 承認の回答：番号キー

**結論**：画面に見えている承認プロンプトを `agent.rs` で解析し、選んだ番号のキーを1文字送る。回答直前に画面を再走査し、プロンプトがなければ拒否する。

**経緯**：Claude Code 2.1.286で、番号キーで選択と確定が行われることを確認した。プロンプトの文言・枠線（実線は境界、点線は枠内の区切り）に依存するため、判定はAdapterに閉じ込めた。

### 16.10 入れ子セッションの環境変数を消す

**結論**：hostはエージェント起動時に `CLAUDECODE`、`CLAUDE_CODE_CHILD_SESSION`、`CLAUDE_CODE_SESSION_ID` などを除く。オーケストレーターの `claude -p` も同様。

**経緯**：daemonがClaude Codeセッション内から起動された場合などに、claudeが子セッションと判断してトランスクリプト保存を止めることを確認したため。

### 16.11 アカウントの識別

**結論**：`CLAUDE_CONFIG_DIR/.claude.json`、未設定なら `~/.claude.json` の `oauthAccount.accountUuid` と `emailAddress` を使う。失敗時は `claude auth status` の出力からメールアドレスを拾う。

**経緯**：design.mdでは `~/.claude` 配下としていたが、既定の場所はホーム直下だった。

### 16.12 マシンの接続方法：sshのみ

**結論**：`~/.codequilt/machines.json` の各エントリは `ssh`（`ssh -T -o BatchMode=yes <host> cq bridge`）だけを持つ。`cq machine add` は `~/.ssh/config` のホストを候補に出す。

**経緯**：一時的に任意コマンドで接続する口を設けたが、最小構成を保つため削除した。WSLは「仮想のリモートLinux」としてsshで扱い、CodeQuiltにWSLの知識は持たせない。

### 16.13 新規起動の許可ルート（仮）

**結論**：`~/.codequilt/config.json` の `allowed_roots`、未設定ならホームディレクトリ配下のみ起動を許可する。

### 16.14 オーケストレーター（仮）

**結論**：
- モデルはhaiku。`--system-prompt` で既定のシステムプロンプトを差し替え、`--tools ""` と `--no-session-persistence` を付け、作業ディレクトリは `~/.codequilt`。`--bare` はOAuthを使わずサブスクリプション枠で動かせないため使わない。
- 600文字を超える返答だけ要約する。要約はライブのイベントだけに行い、localStorageにキャッシュする（再読み込みでトークンを使わない）。
- 宛先は `@名前`（表示名をスラッグ化、重複時はid先頭を付与）→ カードへの返信 → 稼働中が1つならそれ → LLMの推定 → 不明なら候補を選択肢で提示。
- 送信はブラケットペーストで、Enterの自動送信は既定オン（パネルで切り替え）。

**経緯**：ユーザーのグローバルCLAUDE.mdは読み込まれるため、要約は日本語になる。1回あたり約4〜5kトークン（haiku）。

### 16.15 キーバインド（仮）

| 操作 | キー |
| --- | --- |
| セッションをタイルで開く | Alt+1〜9 |
| 前後のタイル | Ctrl+Shift+←/→（PageUp/PageDown） |
| 右・下に分割して次のセッションを開く | Ctrl+Shift+\ / Ctrl+Shift+- |
| タイルを閉じる | Ctrl+Shift+W |
| 承認ダイアログを再表示 | Ctrl+Shift+A |

アプリ側で先に捕まえ、xterm.jsには渡さない。

### 16.16 リモートへのcq配布（仮）

**結論**：当面は手動で配置し、パスが違う場合は `machines.json` の `cq_path` で指定する。プロトコルバージョンの不一致はマシンのエラーとして表示する。自動配布は後で検討する。

## 17. 本体の範囲：ラップと集約に絞る

**結論**：本体はcq host・daemon・CLI・`cq mcp` とプロトコルに限る。ダッシュボードUI、オーケストレーター、音声入力はすべて本体に接続するクライアントとし、クライアント同士は依存しない。全マシンの集約はローカルのdaemonが受け持つ。

**経緯**：当初はダッシュボード内にオーケストレーターと音声入力を置き、続いてダッシュボードがプラグインを起動する案（VS Codeのextension host型）を検討した。しかし「Claudeのプロセスをラップしてハブに繋げる」のが本体で、オーケストレーターはそれらを購読して仲介する一利用者だと整理すると、UIもオーケストレーターも本体から見て対等なクライアントになる。プラグイン同士（UIとオーケストレーター、whisperとオーケストレーター）の依存も、オーケストレーターをセッションとして扱えば生じない。

**採用しなかった案**

- ダッシュボードがプラグインを子プロセスとして起動する方式：UIとオーケストレーター、whisperとオーケストレーターの間に依存が生じ、トピックによる連携などの仕組みが要る。
- プロセス内への静的リンク／dylib／WASM：GPU版とCPU版のwhisperを同梱できない、障害が波及する、GPUに触れない、などの理由（第16章までの検討を参照）。
- 集約専用の新プロセス（`cq hub`）：役割は明確だが常駐プロセスの種類が増える。daemonは状態を持たない中継役なので、リモートへの接続を足しても性質は変わらない。

## 18. オーケストレーターはセッションとして扱う

**結論**：オーケストレーターは `orchestrator` タグの付いた普通のエージェントセッションとし、cq-orchestratorの常駐プロセスが他セッションの出来事を届ける。UIはオーケストレーターを前面に固定できるだけで、オーケストレーター専用の画面は持たない。cq-orchestratorは汎用のオーケストレーターとし、エージェント（claude / codex）・モデル（既定sonnet）・人格・担当範囲・届け方を設定で変えられる。複数のオーケストレーターを同時に置ける。

**経緯**：オーケストレーターはClaudeに限らずCodexでもよく、担当や役割を分けて複数置きたい場合もある。オーケストレーターをセッションにすれば本体はオーケストレーターを特別扱いせずに済み、オーケストレーター自身のトークン消費も他と同じく使用量表示に出る。一方、オーケストレーターは話しかけられないと動かないため、他セッションの出来事を自動で届ける仕組み（第19章）が要る。オーケストレーターを置かない場合はマルチプレクサとして使う。

**採用しなかった案**

- ダッシュボード内のオーケストレーター（`claude -p` で要約・宛先推定）：M4で実装したが、オーケストレーターが一つに限られ、エージェントも固定される。
- 必要なときだけオーケストレーターが情報を取りに行く方式：仲介のたびに状況確認の一手間が挟まり、オーケストレーターを置く意味が薄れる。
- `@名前` を本体やUIの機能にする：名前は本体の機能だが、名前を使った宛先指定はオーケストレーターの役割。

## 19. オーケストレーターへの届け方：ClaudeはChannels、それ以外はPTY注入

**結論**：Claudeで動くオーケストレーターへの通知はChannelsで届ける。Codexや、Channelsが使えない環境では、オーケストレーターがアイドルで入力欄が空のときだけPTYに注入する。

**経緯**：オーケストレーターのタイルはユーザーが常に入力する場所なので、PTY注入だと入力中は届けられず、通知が「ユーザーの発言」として履歴に混ざる。Channelsはこの用途向けに作られた仕組みで、ユーザー環境ではTelegramで利用実績がある。第1章で不採用にした理由（セッションを掴む方式としてClaude専用）は、cq-orchestratorが届け方の一つとして使う分には当てはまらない。ただしcq独自のチャネルが開発用フラグや組織設定を要するかは、実装前に試作で確かめる。

## 20. クライアントが登録するコマンド

**結論**：クライアントは名前付きのコマンドを本体に登録でき、UIはそれをボタンやキーに割り当てて呼ぶ。本体は呼び出しを登録元へ中継するだけ。最初の利用者はcq-whisperのプッシュトゥトーク（押下と解放を区別する）。

**経緯**：グローバルホットキーを使わないと、キー入力を受け取れるのは前面にあるダッシュボードだけになる。UIがcq-whisperを直接呼ぶとクライアント同士が依存するため、VS Codeのコマンドと同様に本体を介した登録・呼び出しにした。

## 21. R2の実装メモ

- **名前とタグ**：`SessionMeta` の `name` / `tags` をhostが持ち、`SetMeta` で変更してファイルに保存する。daemonは1秒ごとの走査で一覧に反映する。`cq claude` では `--cq-name` / `--cq-tag` で付ける（それ以外の引数はclaudeへ渡すため、claudeの引数と衝突しない名前にした）。名前の一意性は強制しない。重複時の扱いはクライアント（cq-orchestrator）が決める。
- **承認のプロンプトID**：プロンプト本文と選択肢のFNV-1aハッシュ。`Approve.prompt_id` が画面上のものと違えば拒否する。
- **アイドル時の注入**：hostが待ち行列を持ち、次の条件がそろったら1件ずつブラケットペーストで入れる。①Stop / SessionStartの後でUserPromptSubmitが来ていない、②承認プロンプトが出ていない、③入力が `quiet_ms` 以上ない、④入力欄が空。④はClaudeのAdapterで、実線直下の `❯` 行以降に「既定色かつdimでない」文字があるかで判定する（プレースホルダーは灰色かdimで描かれる）。
- **フォーカスとコマンド**：デスクトップ単位の状態としてローカルのdaemonがメモリに持つ。リモートのdaemonには中継しない。コマンドは登録したクライアントが切断すると消える。
- **CLI**：`cq rename` / `cq tag` / `cq inject` は `[machine:]id` を受け付け、daemon経由でhostに送り、hostの確認イベント（`meta`、`inject_queued`）を待ってから終了する。

## 22. `cq mcp` の実装

**結論**：MCPサーバーはSDK（rmcp）を使わず、stdioの改行区切りJSON-RPCで `initialize` / `tools/list` / `tools/call` だけを自前で実装した。ツールは `list_sessions`、`get_turns`、`send`、`approve` の4つ。サーバーはdaemonに `federate` で接続し、イベントから各セッションの状態と直近20ターンを組み立てる。宛先は名前・`machine:id`・id前方一致で指定でき、`--scope tag:NAME` / `machine:ID` で範囲を絞る。自分が動いているセッション（`CQ_SESSION_ID`）は対象外。

**経緯**：必要なメソッドが少なく、R5でChannelsの通知を足すときも同じサーバーを拡張するだけで済む。依存を増やさない方を選んだ。

## 23. Channelsの試作結果

- `cq mcp --channel` は capabilities に `experimental: {"claude/channel": {}}` を宣言し、デスクトップのコマンド `channel:<セッションID>` を登録する。そのコマンドが呼ばれると `notifications/claude/channel`（`content`、`meta`）を送り、Claudeには `<channel source="cq" ...>` として届く。
- `--channels` で指定できるのは許可リストに載ったチャネルだけで、cqのような独自サーバーは `--dangerously-load-development-channels server:cq` が必要。この場合、起動のたびに「ローカル開発用として使う」の確認が表示される。`--mcp-config` で渡したサーバーについて「その名前のMCPサーバーがない」と起動時に表示されるが、配信には影響しない（Claude Code 2.1.287で確認）。
- コマンドはデスクトップ単位の仕組みなので、この方式はオーケストレーターがローカルマシンで動く場合に限られる。

## 24. cq-orchestratorの実装

- **構成**：`crates/cq-client`（daemonへの接続と、イベントからセッションの状態・直近ターンを組み立てるモデル。`cq mcp` と共有）と `crates/cq-orchestrator`。`cq-orchestrator start [NAME] [--detach]` が設定（`~/.codequilt/orchestrators/NAME.toml`、無ければ既定値で作成）からオーケストレーターセッションを `orchestrator` タグ付きで起動し、配達役 `cq-orchestrator run NAME` を切り離して起動する。既定ではこの端末にアタッチする。
- **配達役**：担当範囲の承認プロンプト・確認ダイアログ・ターン終了を集め、`batch_seconds`（既定2.5秒）まとめてから、オーケストレーターがアイドルのときに届ける。直接入力（UserPromptSubmit）や解消されたプロンプトは取り下げ、未解決の承認は次の通知に「まだ待っているもの」として添える。接続時の履歴の再送は報告しない。オーケストレーターのセッションが終わると自分も終了する。二重起動はデスクトップのコマンド `orchestrator:NAME` の有無で防ぐ。
- **届け方**：Channelsでは、オーケストレーターのMCPサーバーがチャネルのコマンドを登録する（＝開発用チャネルの確認に答える）まで配信を待つ。PTYでは `Inject`（アイドル・入力欄が空のときだけ）を使う。
- **確認の体験を揃える**：開発用チャネルの確認やフォルダ信頼など、番号で答えるダイアログも承認プロンプトと同様に検出し（`kind: "dialog"`）、ダッシュボードの承認ダイアログからも答えられる。
- **ツールの許可**：`list_sessions` / `get_turns` / `send` は事前許可、`approve` は既定では事前許可せず、使うたびにオーケストレーター自身の承認確認を挟む（`allow_approve = true` で事前許可）。
- **未実装**：`@名前` をオーケストレーターのhookで直接送る近道、Codexで動くオーケストレーター（M5）、リモートマシン上のオーケストレーター（チャネルのコマンドがデスクトップ単位のため）。

## 25. `@名前` の近道と追加設定

- **追加設定の合成**：Claude Codeは `--settings` を複数指定すると最後の1つしか使わない（hooksは合算されない）ことを確認した。そこで本体に汎用の仕組みとして `cq claude --cq-settings FILE`（起動要求では `settings_extra`）を設け、CodeQuiltのhooksと追加ファイルのhooksをイベントごとに連結したセッション専用の設定（`~/.codequilt/settings/<id>.json`）を作る。statusLineはCodeQuiltのものを優先する。
- **`@名前`**：cq-orchestratorはオーケストレーターセッションにUserPromptSubmit hook（`cq-orchestrator hook`）を追加する。`@名前 本文`（`@machine:名前` も可）なら対象へ直接送り、`{"decision":"block"}` を返してオーケストレーターのLLMターンを使わない。該当なしなら素通しでオーケストレーターに任せ、複数該当ならブロックして候補を示す。
- **`prompt_blocked`**：hookでプロンプトを止めると、並行して動くCodeQuiltのUserPromptSubmit hookがセッションを「作業中」にしてしまう。止めたhookが少し待ってから `prompt_blocked` イベントをhostへ送り、hostとcq-clientはセッションをアイドルに戻す（オーケストレーターへの配達が止まらないようにするため）。
- **ハンドルの継承**：Windowsでは子プロセスが親の継承可能なハンドルをすべて引き継ぐため、切り離して起動したプロセスが呼び出し元のパイプを握り続けた。切り離し起動の前に自分の標準ハンドルの継承フラグを外す。

## 26. Codex対応（M5）

- **hooks**：Codex 0.159のhooksはClaude Codeとほぼ同じ（SessionStart / UserPromptSubmit / Stop / PermissionRequest、`transcript_path` と `last_assistant_message` あり、既定で有効）。`--settings` が無いので `-c hooks.<Event>=[...]` で注入する。初回はCodexが「Hooks need review」で信頼を求める（ユーザーの設定に残る）。SessionStartは最初のターンで発火するため、Codexのセッションは起動時からアイドル扱いにする。`-c` を使うと共有バックグラウンドサーバーを使わない組み込みモードになる旨の警告が出るが、動作に影響はない。
- **使用量**：statusLineが無いので、rollout（`transcript_path`）の `token_count` からトークン累計とレート制限（primary=5時間、secondary=週）、`turn_context` からモデルを読む。クライアントが同じように読めるよう、Claudeのstatus line JSONと同じ形に揃えて `statusline` イベントとして流す。アカウントは `~/.codex/auth.json` のid tokenのクレーム（アカウントIDとメール）だけを読む。
- **画面**：Codexの選択リスト（`›`、`enter confirm · esc skip` / `Press enter to confirm or esc to cancel`）も確認ダイアログとして検出する。選択中の行を行末まで反転表示で埋めるため、vt100の `contents()` が行を連結してしまう。行ごとに取り出して判定する。選択肢が「Yes, proceed」等ならpermission扱い。
- **回答と送信**：Codexのリストは数字で即確定するものと選択だけ動くものがあるため、数字を送って0.4秒後も同じプロンプトが残っていればEnterを送る。まとめて届いた入力はペーストとして扱われ末尾のEnterが改行になるため、ペーストの0.5秒後にEnterを送る。
- **起動**：Windowsではnpm / Voltaが拡張子なしのシェルスクリプトと `.cmd` を並べて置くため、PATHEXTを優先して実行ファイルを探し、`.cmd` は `cmd.exe /c` で起動する。
- **未対応**：Codexをオーケストレーターにすること（MCP設定と指示文の渡し方、Channels非対応のためPTY配信）。

## 27. Linux（WSL）での確認と対応

- WSL（Ubuntu 24.04）を「仮想のリモートLinux」として、ローカルdaemon → ssh → WSLのdaemonの経路で、claudeとcodexの起動・hooks・承認・使用量を確認した。
- **PATH**：非対話のsshコマンドでは `~/.bashrc`（対話部分）も `~/.profile` も読まれず、Voltaや `~/.local/bin` のclaude / codexが見つからない。マシン登録に `login_shell`（`cq machine add HOST --login-shell`）を設け、`sh -lc 'exec cq bridge'` で起動して `~/.profile` を反映する。Windowsのリモートには `sh` が無いため既定は無効。
- **TERM**：ssh経由で起動したdaemonには `TERM` が無く、claudeが色なしで描画してプレースホルダーを入力済みと誤判定した。Unixのhostは `TERM` 未設定（またはdumb）なら `xterm-256color` と `COLORTERM=truecolor` を与える。加えてClaudeのプレースホルダー（`Try "…"`）を文面でも判定する。
- **daemonの更新**：Linuxでは実行中のバイナリを置き換えられるが、古いdaemonが動き続ける。プロトコルや起動処理を変えたら、daemonを止めて立ち上げ直す必要がある（停止コマンドは未実装）。

## 28. セッションの終了（`cq kill`）

- **背景**：Claude CodeのRemote Controlが有効だと、正常終了（`/exit`、Ctrl+C 2回など）したセッションはアーカイブされるが、プロセスを強制終了したセッションはサーバーに終了が伝わらず、モバイルアプリ等で生きているように残り続ける（サーバー側のタイムアウトは確認できなかった）。CodeQuiltにはセッションを終わらせる手段がなく、テストで強制終了したセッションが残骸になっていた。
- **結論**：hostに `Terminate { grace_ms, force }` を追加し、hostがエージェントにユーザーと同じ操作で終了させる。Esc（ダイアログを閉じる・ターンを止める）→ Ctrl+C を3回（入力を消し、2回目以降で終了）→ まだ動いていれば Ctrl+C の後に終了コマンド（Claude `/exit`、Codex `/quit`）を入力。猶予（既定10秒）内に終わらなければ強制終了する。`force` は即座に強制終了。画面の状態を知っているhostが行うので、CLI・ダッシュボード・リモートのどこからでも同じ手順になる。
- **使う場面**：`cq kill <名前|id>`（`--force`、`--grace 秒`）と、ダッシュボードのセッション一覧の「End session」（確認あり）。タイルを閉じる操作は「見えなくしたい」だけのことが多いためデタッチのまま。オーケストレーター・MCPからの終了は影響が大きいので今は提供しない（入れるなら承認と同様に既定で無効）。daemonの停止やマシンの終了ではセッションに触れない。
- **検討した選択肢**：クライアント側で入力を送る（リモートや複数クライアントで手順が分散する）、SIGTERMを送る（Windowsに相当がなく、Claude CodeがRemote Controlを片付けるかも不明）。
- **注意**：`Terminate` を知らない古いhostに送ると接続が切れる。hostを更新するまでは使えない。

## 29. プラグインの外部サブコマンドとエイリアス

- **結論**：`cq NAME` が組み込みでなければ `cq-NAME` を探して実行する（cq本体のディレクトリ → `PATH`、Windowsは `PATHEXT` 順、`.cmd` は `cmd /c`）。Unixはexecで置き換わり、Windowsは子として実行して終了コードを返す。Windowsでは親が先に終わってプロンプトが戻らないよう、待っている間のCtrl+Cは親で握りつぶす（ハンドラ関数を登録する方式。「無視」の設定は子に継承されるため使わない）。
- **エイリアス**：既存の `config.json` に `aliases` を足した。値は複数語でもよい。既定は `o = orchestrator`。組み込みのサブコマンドとその別名が常に優先し、エイリアスで既存コマンドの意味を変えられないようにした。前方一致の自動解決は、コマンドが増えたときに同じ入力の意味が変わるので採らない。
- **検討した選択肢**：cq本体にorchestrator用のサブコマンドを書く（本体がプラグインに依存する）、プラグインを本体に登録して呼ぶ（導入の仕組みが要る。コマンドパレット用のmanifestの検討で扱う）。

## 30. 設定ファイルをTOMLに統一

- **結論**：人が編集する設定（`config.toml`、`ui.toml`、`keybindings.toml`、`orchestrators/NAME.toml`）はTOMLに揃える。`config.json` と `machines.json` は `config.toml` の `allowed_roots` / `[aliases]` / `[[machines]]` にまとめ、最初の読み込み時に自動で変換して元ファイルを `.bak` に残す。`cq machine add/remove` は `toml_edit` で編集し、ユーザーのコメントや並びを保つ。設定が壊れているときは警告して空の設定として扱い、セッションの動作は止めない。
- **対象外**：プログラムが生成する状態（`sessions/*.json`、`plugins/*.json`）と、Claude Code・MCPがJSONを要求するファイル。
- **検討した選択肢**：YAML（書き味は良いが、Rustの定番だった `serde_yaml` が保守終了しており後継が分散していること、コメントを保った編集の手段が無いこと、インデント依存と暗黙の型変換）。JSON（コメントが書けない）。TOMLは配列が `[[...]]` とやや冗長だが、既にオーケストレーターの設定とCargoで使っており依存も1つで済む。

## 31. コマンド・キーバインド・UI設定の実装

- **名前**：プロトコルの既存フィールドに合わせ、manifestでもコマンドの識別子は `name` とした（設計段階の `id` から変更）。
- **プラグインの把握**：daemonは起動時に本体の隣の `cq-*` のmanifestを取り込み（実行ファイルの方が新しければ取り直す）、`~/.codequilt/plugins/*.json` を数秒ごとに読み直して変化があれば `CommandList` を配る。ファイル監視ライブラリは入れていない。
- **キーの判定**：`KeyboardEvent.code` から組み立てるため、配列に依存しない（JISの `ろ` / `¥` キーも `\`）。IMEで変換中のキーはコマンドにしない。割り当てのあるキーだけをターミナルより先に取り、それ以外はxtermに渡す。
- **設定の反映**：`ui.toml` / `keybindings.toml` はUIのバックエンドが1秒ごとに更新時刻を見て、変わったら読み直して画面に送る。フォントは既存のターミナルにもその場で反映する。
- **警告**：設定ファイルの構文エラー、未知のコマンド、既定のキーの上書き、同じ層での重複はコマンドパレットの下に表示する。
- **不具合の修正**：連携先（リモート）のdaemonが送る空の `CommandList` がローカルの一覧を上書きしていた。フォーカスとコマンドはデスクトップ単位の状態なので、リモートからは中継しない。

## 32. boardの起動時hookとdaemonの操作

- **起動時hook**：`ui.toml` の `[[on_start]]` にコマンドを並べ、boardの起動時に実行する。既定値はコードに隠さず、`ui.toml` が無ければ書き出す（既定は `orchestrator.start`）。失敗は黙って飛ばさず、すべて通知する。
- **daemonの自動起動はhookにしない**：daemonが無いとboardは何もできないので、外せる設定にしても壊れた構成が増えるだけ。接続する側（cq-client）が起動する仕組みのままにした。
- **daemonの停止・再起動**：プロトコルに `Shutdown { machine }` を足した。再起動は「止める → 次の接続が起動する」で実現し、専用の仕組みを作らない。リモートはbridgeの再接続が新しいdaemonを起動する。
- **重複起動の防止**：`orchestrator.start` は同名・`orchestrator` タグのセッションが動いていれば成功として何もしない。連続した起動でも確実にするため、daemonは `Launched` をcq hostがセッションを登録した後に返す。
- **見つけた不具合**：unixではソケットをbindすると既存のファイルを置き換えるため、`cq daemon` を二重に起動すると後のものが前のものを奪っていた。bindの前に既存のdaemonへの接続を試す。また、Windowsの名前付きパイプはサーバーが次の受け口を作る間「ビジー」になり、待ち時間なしの接続確認が「daemonが無い」と誤判定して新しいdaemonを起動していた（停止直後に残ることがあった）。ビジーは生存の印として、常に少し待つ。

## 33. タグの廃止と名前の一意化

- **背景**：タグの用途はオーケストレーターの目印（二重起動の防止、courierがオーケストレーターを探す、自動ピン留め）と範囲指定（`--scope tag:NAME`）だったが、実際に効いていたのはオーケストレーターの目印だけだった。
- **結論**：タグを廃止し（`SessionMeta.tags`、`Launch.tags`、`SetMeta` のタグ操作、`cq tag`、`--cq-tag`）、名前の変更は `Rename { name }` だけにした。代わりに「動いているセッションの名前はマシンごとに一意」を本体の決まりにし、重複する名前での起動（`--cq-name`、boardからの起動）や改名は断る。オーケストレーターは名前だけで確実に特定できる。範囲指定は `machine:ID` だけを残し、cq mcpとcourierで重複していた実装をcq-clientにまとめた。
- **ピン留め**：`ui.toml` の `pinned`（名前の一覧、既定 `["orchestrator"]`）で決め、一覧の📌による個別の選択がそれより優先する。
- **検討した選択肢**：cq-orchestratorが起動したセッションのidを記録する案は、ターミナルにアタッチして起動する経路（中で `cq claude` を実行）ではidを事前に知れないため採らなかった。

## 34. 読まれないファイルの廃止とドキュメントの分担

- **hookのスプールとstatusLineのファイル**：hookは `~/.codequilt/spool/<id>.jsonl` に、statusLineは `~/.codequilt/status/<id>.json` に書いていたが、どこからも読まれていなかった（当初はクライアントの起動時に状態を復元する想定だったが、cq hostが履歴を持って再送する形になり不要になった）。どちらも書かないようにした。
- **ドキュメント**：`design.md` は現在の設計、`features.md` は機能・コマンド・設定・データの置き場所、`decisions.md` だけが経緯を持つ形に分けた。ロードマップや完了済みの試作の記述は `design.md` から外した。常駐プロセスはコードと同じ名前（`cq daemon`／daemon、`cq host`）で呼び、通称は使わない。

## 35. 新規セッションのフォルダ

- **結論**：「New session」では、そのマシンのClaude Code（`.claude.json` の `projects.<dir>.hasTrustDialogAccepted`）とCodex（`config.toml` の `trust_level = "trusted"`）で信頼済みのフォルダを候補として出し、それ以外は「Choose another folder…」で `allowed_roots` の配下から選ぶ。信頼済みのフォルダは `allowed_roots` の外でも起動を許す（ユーザーがエージェントで明示的に信頼したため）。CodeQuiltの状態ディレクトリ（オーケストレーターの作業フォルダ）は除く。どちらも要求のたびに読み直し、キャッシュしない。
- **検討した選択肢**：`allowed_roots` から辿るだけ（よく使うフォルダに毎回辿り着く手間がかかる）。CodeQuilt独自の「最近使ったフォルダ」の記録（エージェントの信頼の記録と二重になる）。

## 36. ダッシュボードの画面（タブとペイン）

- **タブの中にペイン**：エディタ（VS Code）は「分割の中にタブ」だが、CodeQuiltのセッションは長く動き続ける端末なので、tmux・i3と同じく「タブ（ワークスペース）の中にペインを並べる」形にした。分割すると空のペインがすぐ現れる（i3で分割しても見た目が変わらない不満から）。一覧から開くときは、空のペインを埋めるか、親と逆の向きに分割する（bspwmのdwindleと同じ）。
- **自前の実装**：dockviewはVS Code型（分割の中にタブ）で、順序を入れ替えると部品と戦うことになるため外し、分割の木構造と境界のドラッグだけを持つ小さな部品で作った。
- **表示中のタブだけ描く**：PTYの大きさはセッションに1つしかないので、同じセッションを複数のタブに置けるようにしつつ、描くのは表示中のタブだけにした。裏のタブを描き続けると大きさの違う端末に出力が流れて崩れるため。代わりにタブを切り替えるとスクロールバックが消える（残すにはcq hostがスクロールバックを持つ必要がある）。
- **承認は右下のカード**：中央のダイアログは入力のフォーカスを奪い、ペインで打っている文字や Enter が回答になる危険がある。フォーカスを奪わないカードにし、最小化しても右サイドバーの一覧から戻せるようにした。
- **キーのヘルプは置かない**：左下に固定のキーのヘルプを出す代わりに、すべてのコマンドとキーを一覧・編集できる画面（`ui.keybindings`）を設けた。

## 37. ディレクトリごとのトークン

- **CodeQuiltのセッションだけを数える**：`~/.claude/projects` やCodexの `sessions` を全部走査すればCodeQuilt外の利用も数えられるが、各マシンでの走査とdaemonの新しいメッセージが要る。まずはcq hostが知っているセッションに限り、メタデータに残して終了後も数える。
- **1時間ごとに記録する**：累計だけだと、長く動くセッション（オーケストレーターなど）の使用量を期間で切れない。ログの各行の時刻で1時間ごとに分けてメタデータに書く。保存は1分に1回と終了時にし、daemonが一覧を送り直す回数を抑える。
- **合計にキャッシュを含める**：セッションの行の `tokens:` と同じく入力・出力・キャッシュの読み書きの合計にした。内訳はツールチップで見る。

## 38. アイコン

- **lucideに統一**：文字や絵文字（✕・⏻・📌など）はフォントで見た目が変わり、豆腐にもなる。手書きのSVGは保守が要る。react-iconsは複数のセットが混ざり見た目が揃いにくく、@tabler/icons-reactはlucideに勝る点がないため、線の太さが揃い使う分だけバンドルされる `lucide-react` にした。
- **形で操作を分ける**：同じ✕がデタッチと終了の両方に使われていて区別できなかった。VS Codeのターミナルと同じく、表示を閉じるだけなら✕、セッションの終了はゴミ箱、デタッチはログアウトにした。

## 39. ペインのドラッグは「分割して移る」だけにする

- **入れ替えをやめた**：中央に落とすと入れ替え、端に落とすと分割、と同じドラッグで結果の種類が変わっていた。入れ替えはあまり期待されない操作で、2回の移動で同じ結果にできる。タブをまたいで入れ替えると相手のセッションも元のタブへ移るので、重複の確認も両方向に要る。
- **空のペインも埋めない**：空のペインだけ「そこに入れる」にする案もあったが、一貫性を優先し、どのペインでも対角線で決まる方向に分割する。
- **タブの上で待つと切り替える**：タブに落とすだけでは移った先での置き場所を選べないため、少し待つとそのタブを表示し、そのままペインに落とせるようにした（ブラウザでタブの上にファイルを持っていくのと同じ）。
- **不正な移動は元に戻して知らせる**：同じセッションを同じタブに2つ置くことはできないので、黙って何もしないのではなく、元の表示に戻してトーストで理由を出す。

## 40. 左サイドバーの整理

- **欄を隠す機能をやめた**：Pinned・Tabs・Machinesを欄ごとに隠すボタンとコマンドがあったが、折りたたみでほぼ同じ目的を果たせるため、1つの仕組み（折りたたみ）に寄せた。
- **セッションの行を1つの部品に**：Tabsだけ簡易な行で詳細もピンも終了もなかった。どの欄でも同じ操作ができるよう同じ部品にした。詳細の展開状態は欄ごとに分け、Machinesで開くとPinnedでも開く、ということを無くした。
- **MachinesにActiveの階層**：Endedと対にし、TabsとMachinesでセッションの行の字下げを揃えて、幅に対して1行に出る情報量を同じにした。
- **サイドバーの開閉ボタンは2段目**：タイトルと同じ行に置くと、アプリ全体のメニューを置く場所がなくなるため、タイトルの下に1段設けた。

## 41. サイドバーの開閉ボタンはタイトルと同じ段に戻す

- #40で開閉ボタンのためにタイトルの下に1段設けたが、ボタン2つのために1段使うのは無駄が大きいため、タイトルと同じ段の右端に置いた。アプリ全体のメニューが要るようになったら改めて考える。
- 左サイドバーの字下げは1階層ごとに同じ幅にし、セッションの行の開始位置はPinned・Tabs・Machinesで揃える（いちばん深いMachinesに合わせる）。

## 42. ペインの見出しのボタンは✕だけにする

- ペインの見出しにデタッチ（ログアウト）と終了（ゴミ箱）を並べていたが、ペインを閉じるのはタブや空のペインを閉じるのと同じ「表示を閉じる」操作なので✕に揃え、終了は左サイドバーの行のゴミ箱だけにした。ペインのすぐ横に終了を置くと押し間違えやすい。
- スクロールバーは細く暗い色にし、左サイドバーはスクロールバーの幅を常に確保して、出る前後で1行に出る情報量が変わらないようにした。

## 43. セッションの行の列幅

- 状態の文字列（idle / working / needs approval）の長さでidの位置がずれていたので、名前とidを固定幅の列にした。状態は残りの幅に入れ、入りきらなければ省略する。
- 幅の変え方は、表の見出し行を1行置く案もあったが、常に1行を使うため、どの行でも列の右端をドラッグする形にした（境界はホバーで示す）。

## 44. 右サイドバーの欄の名前と表記

- レート制限の欄は「Usage」だと Tokens（使用量）と紛らわしいので「Limits」にした。
- Tokens のエージェントとアカウントの表記は Limits と同じ部品（エージェント名を白、アカウントを灰色、コロンなし）にした。

## 45. キーの割り当ては置き換え

- キーバインドの画面の操作を「キーを追加」から「置き換え（bind）」にした。ユーザーが最初に期待するのは置き換えで、VS Codeでも主な操作は「Change Keybinding」。1つのコマンドに複数のキーを持たせたい場面は少なく、`keybindings.toml` を直接書けば今もできる。
- 使用中のキーを割り当てるときは確認して元のコマンドから外す。そのため「どのキーがどのコマンドを上書きしたか」の警告はやめ、未知のコマンドと書式の誤りだけを警告にした。
- `tab.goTo` のように引数違いで複数のキーを持つコマンドは、引数ごとに1行として扱い、行ごとに1キーにした。

## 46. ピンのボタンはホバーで出す

- ピンのボタンは常に薄く出していたが、ゴミ箱と同じくホバーしたときだけ出すようにして行の見た目を揃えた。ピン留めしたセッションは横向きのピンを常に出し、Pinned以外の欄でも見分けられるようにした。

## 47. オーケストレーターのcqが見つからなければ起動しない

- cq-orchestratorの隣にcqが無いとき（cq-orchestratorだけをビルドした直後など）、`NAME.mcp.json` に `cq.exe` という名前だけを書いていた。Claude Codeは `PATH` 上の別の（古い）cqを起動しうるので、絶対パスが得られなければオーケストレーターの起動を失敗させる。`PATH` から探して絶対パスにする案は、同じく古いcqを拾いうるため採らなかった。

## 48. OS通知をやめる

- boardはターン終了と承認待ちをOS通知で出していたが、試用では役に立たず、並列のセッションのターン終了が続けて届いてうるさかった。ボードを見ている間は、行の状態、Approvals、承認のカード、オーケストレーターの報告で足りている。
- 通知の設定を持たせる案や、boardから独立したプラグインにして通知するイベントを選べるようにする案は、今は使う予定がないため採らなかった（YAGNI）。通知の上で返信の入力や承認ができるなら価値があるので、cq-notifyの構想として `design.md` の未決事項に残した。
- 承認待ちのときだけタスクバーを点滅させる案は、困ったら足すことにした。

## 49. 音声入力（cq-whisper）は作らない

- 音声入力はクライアントcq-whisperとして足す予定だったが、OSの音声入力（WindowsのWin+H、Ubuntu 26.10以降のデスクトップ統合の音声入力）がboardの端末にもそのまま入り、目的を概ね満たすため作らない。入力先はLLMなので多少の誤認識は文脈で補われる。
- Win+Hは英語の技術用語に弱い。開発用語に強いClaude Codeの `/voice` は、cq host配下のセッションでも使えることを確かめた（boardからオーケストレーターに話しかけられた）。ほかにWispr Flowなどの他社製の全体音声入力もある。
- 自前で実装する案（whisper.cppをローカルで動かす、クラウドの文字起こしAPIを使う）は、録音・認識エンジン・モデル配布を抱える割に、cqならではの価値がセッション名などを認識のヒントにできる程度しかないため採らなかった。

## 50. 押しっぱなしのコマンドをやめる

- #20でcq-whisperのプッシュトゥトーク向けに、コマンドの `hold` と、押下・解放を区別する `phase`（`press` / `release`）を入れていた。#49でcq-whisperを作らないことにし、使うプラグインがなくなったので削除した。コマンドの呼び出しは1種類になり、boardは常に結果を待つ。必要になったら足し直す。

## 51. オーケストレーターがセッションを起動する（`launch` ツール）

- オーケストレーターには起動の手段がなく、頼んでも「権限がない」と答えていた。`cq mcp` に `launch` ツール（`cwd`、`agent`、`machine`、`name`、`prompt`）を足した。起動はboardのNew sessionと同じ `Launch` を使うので、ディレクトリの制限（`allowed_roots` か信頼済み）も同じ。Codexで動くオーケストレーターも同じツールを使える。
- 最初の指示は、アイドル時の注入の待ち行列に入れる。起動直後のフォルダ信頼などのダイアログが済み、入力欄が空でアイドルになってから入る。エージェントのCLIに初期プロンプトとして渡す案はエージェントごとに渡し方とダイアログとの順序が違うため、起動後にオーケストレーターが `send` する案はダイアログと競合するため採らなかった。
- `launch` は事前許可した。ディレクトリの制限が安全装置になり、起動したセッション自身の承認はいつも通り求められる。`allow_approve` のような設定で毎回確認させる案は、設定が増える割に得るものが小さいため採らなかった。
- セッションを終了するツールは、オーケストレーターに終了まで任せるかを決めきれないため足していない。

## 52. daemonの停止・再起動はローカルだけ

- boardの `daemon.restart` は引数 `machine` を持ち、パレットで毎回マシンIDを聞かれて煩わしかった。存在しないIDを打つと黙って無視されるのに成功のトーストが出る問題もあった。
- リモートのdaemonを再起動するのは、リモートの `cq` を更新したときくらいで、そのときはビルドのためにリモートの端末を開いている。そこで `cq daemon restart` すれば足り、ローカルのdaemonはsshの接続をつなぎ直す。そのため、boardのコマンドだけでなく、CLIの `--machine` と、`Shutdown` のマシン指定とリモートへの中継もやめた。
- コマンドを「ローカル用」と「リモート用（ID指定）」に分ける案は、ID入力の問題が残りコマンドも増えるため採らなかった。boardからリモートを再起動したくなったら、IDを打たずに済むよう左サイドバーのMachinesのマシンの見出しに操作を置く。

## 53. cq-notifyは今は作らない

- #48で未決事項に残したcq-notify（boardから独立した通知のプラグイン）は、今は作らないことに決めた。未決事項からは外し、構想は#48に残す。

## 54. Codexで動くオーケストレーター

- **エージェントの選び方**：`NAME.toml` の `agent` を既定とし、起動時の `KEY=VALUE`（Hydraのような上書き）で切り替える。エージェントだけ特別に `--agent` を設ける案より、どのキーも同じ仕組みで上書きできる方が単純。値はCodexの `-c` と同じくTOMLとして読む。上書きは保存しない。パレットの `orchestrator.start` には `agent` の引数だけ足し、空なら設定のままにする（任意のキーを打つ欄はパレットでは使いにくいため設けない）。
- **エージェントごとの既定**：`model = "sonnet"` のまま `agent=codex` で起動するとCodexにSonnetを渡してしまうため、`model` と `delivery` は書かなければエージェントごとの既定（Claudeは `sonnet` と `channels`、Codexはユーザーの既定モデルと `pty`）にし、既定の設定ファイルにも書き出さない。Codexの既定モデルを軽いモデルに固定する案は、アカウントによって使えないため採らなかった。
- **Codexへの渡し方**：MCPは `-c mcp_servers.cq.*`、確認なしで使えるツールは `mcp_servers.cq.tools.<tool>.approval_mode = "approve"`（サーバー全体の既定は `prompt`）、人格は `developer_instructions`（ユーザーのAGENTS.mdとは別に読まれる）。オーケストレーターの `cwd` にAGENTS.mdを書く案は、`cwd` をユーザーのプロジェクトにしたときにぶつかるため採らなかった。値は英数字といくつかの記号以外を `\u` でエスケープしたTOMLの文字列にする。Windowsでは `codex.cmd` 経由で起動するため、人格の `<` や `"` を `cmd.exe` が解釈してCodexが起動直後に終了したことから（JSONの文字列として書くだけでは足りなかった）。
- **届け方**：CodexにはChannelsに当たる仕組みがないため、PTY注入にする。`codex queue`（Codexの待ち行列）は、`-c` で起動したセッションで使えるか未確認で、配信が最大10秒遅れ、宛先のスレッドIDが最初のターンまで分からないため採らなかった。

## 55. `@名前` の近道をやめる

- #25で入れた `@名前 本文`（オーケストレーターのUserPromptSubmit hookで直接送る）をやめた。オーケストレーターに代行させないなら、ユーザーは対象のセッションのペインで直接入力する方が自然で、使われなかった。Codexで動くオーケストレーターでこのhookがエラーになったことも見直すきっかけになった。
- これだけのためにあった本体の追加設定（`--cq-settings`、起動要求の `settings_extra`、セッション専用の `settings/<id>.json`）と、プロンプトを止めたことを知らせる `prompt_blocked` イベントも削除した。

## 56. Codexへの注入の送信確認と、オーケストレーター同士の報告

- Codexで動くオーケストレーターに届けた報告が、送信されずに入力欄に残ることがあった。WindowsのCodexは長い貼り付けを速い打鍵として読むため、貼り付けの0.5秒後のEnterが改行として取り込まれる。Codexの入力欄（最後の `›` の行から空行まで、案内文は薄い色）が空かを判定できるようにし、注入した文字が残っていれば1.5秒ごとにEnterを送り直す（最大10秒、誰かが入力したらやめる）。Enterまでの待ちを延ばす案は、文の長さや端末の速さに左右されるため採らなかった。入力欄の判定は、書きかけの文がある間は注入しないことにも使う（これまでCodexは常に空とみなしていた）。
- Claude用とCodex用のオーケストレーターを同時に動かすと、互いのターン終了を報告し合い続けた。courierは自分のオーケストレーターに加えて、courierが動いている（デスクトップのコマンド `orchestrator:NAME` がある）セッションも報告しない。
- 開発用に、`cq debug-screen --session ID` で動いているセッションの画面と、判定の結果を表示できるようにした。

## 57. `cq ls` は動いているセッションだけ

- 終了したセッションが溜まると一覧が読めなくなるため、`cq ls` は動いているセッションだけを出し、`--all` で終了したものも出す。

## 58. resumeは同じIDで復元する

- これまでresumeは、エージェントの会話を引き継いだ新しいセッション（新しいcqのID）として起動していた。元のセッションを復元するという期待と違い、一覧に同じ作業が別のIDで並ぶため、同じcqのIDのまま、記録にあるエージェント・cwd・名前で起動し直すようにした。cq hostは同じIDの記録からエージェント側のセッションID・アカウント・トークンを引き継ぐ。
- 起動要求は、エージェントの会話IDを渡す `Launch.resume` をやめ、cqのIDで指す `Resume` にした。boardのResumeと `cq resume` が同じ処理（`launch::resume_detached`）を使う。
- 最初のターンの前に終わったセッション（Codexは最初のターンまで会話を作らない）は、エージェントを新しく起動する。会話がないからとResumeを出さないと、終了したセッションの中で扱いが分かれて分かりにくい。

## 59. 確認の後の状態とCodexの起動直後

- Codexのセッションが、起動時の確認（更新の案内など）に答えた後 `working` のままになった。確認の解消は「作業中に戻る」とみなしていたが、CodexはSessionStartを最初のターンまで出さないため。hostは確認の解消（`permission_resolved`）に、エージェントがターンの間にいるか（`idle`）を載せ、クライアントはそれで戻り先を決める。クライアント側で確認の前の状態を覚えておく案より、hostの判定1か所で済む。Codexのセッションは、hostと同じくクライアントでも起動時からアイドルとして扱う。

## 60. エージェントのバッジ

- 左サイドバーのセッションの行に、エージェントを色分けした斜線のバッジを折りたたみの右に置き、LimitsとTokensのエージェント名もこのバッジにして、エージェントの見た目を1つにした。

## 61. boardからの名前の変更

- セッションの名前はboardからも変えられるようにした（左サイドバーとペインの見出しで名前をクリック）。重複はhostが断るが、boardはその知らせを受け取る手段を持たないため、board側でも動いているセッションの名前と照らして入力欄で知らせる。

## 62. Endedのディレクトリと選択中の行

- Endedは作業ディレクトリごとにまとめた。終了したセッションは作業単位（ディレクトリ）で探すことが多いため。
- 選択中の行（コマンドパレット、フォルダの一覧、左サイドバーで開いているセッション）の背景をホバーより明るい `--selected` にそろえた。空のペインのセッション一覧のidは、コピーできるように見えていたので、コピーの見た目を左サイドバーのidだけにした。

## 63. 作業ディレクトリは末尾の名前で出す

- 作業ディレクトリはフルパスだと幅を取るため、boardのどこでも末尾の名前で出し、フルパスはカーソルを置いたときに出す。まとめる単位はフルパスのままなので、同じ名前の別のディレクトリは別の項目になる。

## 64. 左サイドバーの階層

- Activeも作業ディレクトリごとにまとめ、セッションの行はどの欄でも4階層目（マシン→Active / Ended→ディレクトリ→セッション）に置いて、エージェントのバッジの位置をそろえた。それ以外の見出しは階層ごとに1段ずつ下げ、1段は半角1文字ほどに狭めた。見出しの左の余白を行と同じにし、折りたたみのアイコンが1段ずつずれて見えるようにした。Activeのディレクトリは、セッションの状態が変わるたびに並びが動かないよう名前の順にした。
- 右サイドバーも左と同じくスクロールバーの幅を常に確保し、出る前後で表示が変わらないようにした。右サイドバーのエージェントのバッジは見出しなので少し大きくした。

## 65. セッション同士のメッセージ（ワーカー用のcqのMCP）

- ワーカーのセッションがBashで `cq inject` を叩いて別のセッションに話しかけられたことから、エージェント同士のやり取りを正式な機能にした。cqで起動したセッションには、ワーカー用のcqのMCP（`cq mcp --worker`）を確認なしで使える形で入れる。
- 渡し方はMCPにした。CLIの使い方を説明するスキルは、エージェントごとに置き場所が違い、ユーザーの `~/.claude` などに書き込む必要があり、Bashの許可も毎回求められるため採らなかった。
- ワーカーが使えるのは `list_sessions` / `get_turns` / 新しい `message` だけにした。`message` は相手がアイドルになってから入力し（`cq inject` と同じ待ち行列）、先頭に `[from 送信元]` を付けて人からの指示と区別させる。すぐに入力する `send`、承認、セッションの起動はオーケストレーターだけに残す。応答し合い続けないよう、ツールの説明で必要なときだけ返信するよう求める。
- オーケストレーターは自分のcqのMCP（`cq` という名前）を持つため、同じ名前のサーバーが2つにならないよう、起動要求の `no_mcp`（`cq claude --cq-no-mcp`）でワーカー用を入れない。

## 66. 狭いサイドバーでのセッションの行

- 左サイドバーを狭くすると、終了したセッションの「15m ago」が折り返して2行になり、名前とidの固定幅の列が行の背景の外にはみ出した。行は常に1行にし、状態（時間）→ id → 名前の順に省略して、よく押すピン・終了・Resumeのボタンは残す。名前には最小幅を付け、それ以上狭いときはボタンが隠れてもよいことにした（名前が読めない行のボタンは使いにくいため）。

## 67. オーケストレーターの名前をorchestratorにする

- 蜂の巣になぞらえてQueen（cq-queen）と呼んでいたが、由来を知らないと役割が伝わらないため、一般的な名前のorchestratorに改めた。プラグインは `cq-orchestrator`、サブコマンドは `cq orchestrator`、組み込みのエイリアスは `o`、パレットのコマンドは `orchestrator.start`、既定のセッション名は `orchestrator`、設定は `~/.codequilt/orchestrators/` にした。過去の記録の名前もあわせて直した。
- 後方互換は持たない。既存の `queens/` と `ui.toml` の `queen` は手で移す。
- 検討した選択肢：エイリアスを `orch` にする案（意味は読み取りやすいが長い）、既定のセッション名だけ `orch` と短くする案（コマンド名と揃わない）。

## 68. 共有crateの名前をcq-protocolにする

- `cq-proto` は略称で何の crate か分かりにくいため、略さず `cq-protocol` にした。

## 69. ワーカーが出したファイルをboardで見る

- エージェントが作った画像や文書を、端末にパスを出すだけでなくboardで見られるようにした。ワーカー用のcqのMCPに `share_file(path, caption)` を足し、共有したファイルの一覧はセッションのメタデータ（`files`）に持つ。boardはそのセッションの端末の右に縦に並べ、選ぶとセッションの右に分割したペインで開く。中身は `ReadFile` でそのマシンのdaemonから読み、daemonは `files` にあるパスしか読まない。要求と応答の仕組みは `ListDir` と同じで、リモートのマシンにもそのまま届く。
- **明示的に送る方式にした理由**：端末に出たパスをリンクにする案は、エージェント側の対応が要らない代わりに、折り返したパスや相対パスの判定が不安定で、boardから任意のパスを読む口にもなる。
- **中身をイベントに載せない理由**：cq hostはイベントの履歴を全クライアントに再送するので、画像を載せると接続のたびに重くなる。メタデータにパスだけを持てば、セッションの終了後も開ける。
- **ファイルの中身は生のバイト列で送る**：JSONの数値配列やbase64にすると大きさが数倍になるため、`FileContent` は `[u64 id][バイト列]` にした。フレームの上限（16MB）に収まるよう、共有できるのは10MBまで。
- **ペインの中身をviewキーに一般化した**：ペインの `session` を `view` にし、ファイルは `file:` で始まるキーで表す。ファイル用のペインの種類を別に設けると、開く・移す・重複を断る処理をそれぞれ書き分けることになるため。保存済みの配置の形式が変わるので、保存のキーを `cq.tabs.v2` に改めた（以前の配置は読まない）。
- **端末の右に並べる理由**：共有したセッションのすぐそばで気づいて開けるようにするため。応答の直下（入力欄の上）に差し込む案は、端末の描画をエージェントが持っていて場所を作れないため採れない。端末の文字に重ねる案は文字を隠し、描き直しで位置もずれる。応答中のファイル名をリンクにする案は折り返しに弱い。端末の下に横に並べる案は入力欄の下で目に入りにくい。右サイドバーにまとめる案は、一覧を見に行く手間がかかり、どのセッションのものかも離れて見える。画像は縮小して見せ、それ以外はファイル名を出す。画面に出ていないセッションの共有にも気づけるよう、ボードを開いている間の共有はトーストでも知らせる。
- **表示**：HTMLはスクリプトを許したsandboxのiframe（同一オリジンは許さない）、Markdownは `marked` でHTMLにしてスクリプトを許さないiframeに入れる。iframeに隔離するのでDOMPurifyなどのサニタイズは入れない。
- 新しいメッセージを足したので、daemonのプロトコルのバージョンを3に上げた。

## 70. マシンの登録をsshの接続先と名前で行う

- `cq machine add {IP}` で登録できるようにした。HOSTは `[USER@]HOST`（IPアドレス、ホスト名、`~/.ssh/config` のHost）で、`-p` でポート、`-n` で名前を付ける。登録内容は `cq machine set` で変え（名前だけを変える `rename` は `set -n` と重なるので持たない）、`remove` で消す。`~/.ssh/config` のHostから番号で選ぶ機能は削った。
- **パスワードを聞かれないsshを前提にする**：sshを張るのは端末を持たないdaemonで、クライアントの接続ごとに張り、切れると5秒おきに張り直す。WindowsのOpenSSHは接続の多重化（ControlMaster）もできない。パスワード認証は聞く先も機会もないため成り立たない。鍵の用意はユーザーに任せ、cqは案内も代行もしない。
  - 検討した選択肢：登録時にパスワードで一度入り、公開鍵を送り込む案（ssh-copy-id相当。今は不要とした）。接続のたびに `SSH_ASKPASS` でboardにパスワードを聞く案（daemonの再起動・切断・スリープのたびに聞くことになり、boardが無いとつながらない）。登録時のパスワードをOSの資格情報ストアに保存してaskpassで渡す案（パスワードの変更後に古いパスワードで5秒おきに再試行して社内アカウントをロックしかねず、他のサービスと共通のパスワードが漏れる被害も大きい。登録時にパスワードを入れられるなら鍵を置けば同じ手間で済む。公開鍵が禁止された環境に当たったら改めて考える）。Rustのsshライブラリで接続する案（`~/.ssh/config`・ssh-agent・known_hostsがそのまま効かなくなる）。
- **登録時に必ずつないで確かめる**：daemonと同じ方法でつなぎ、OSとホスト名を調べて、`cq bridge` がプロトコルのバージョンの合う `Hello` で応えることを確かめる。通らなければ登録しない。つながらないマシンを登録しても使えないため、確かめずに登録する `--force` は持たない。
- **idと名前を分ける**：名前を変えると、それを指すboardのペインの配置・ピンやオーケストレーターの `scope` が切れる。登録時に内部のidを決めて変えず、ユーザーには名前だけを見せる。`scope` は手で書く設定なので名前で書く。手元のマシンの名前は打ちやすさとどのPCから見ても同じであることを優先して `local` に固定した（ホスト名にする案は打ちにくく、WSLのようにホスト名がWindowsと同じマシンと衝突する）。名前の既定はリモートのホスト名で、重複したら連番を付けずにエラーにして `--name` を求める。
- **`login_shell` をやめてOSで決める**：登録時に調べたOSがUnixなら常に `sh -lc` 経由で `cq bridge` を起動し、Windowsなら直接起動する。毎回フラグで指定させる理由がないため。
- **つながらない理由を見せる**：sshの標準エラーを捨てていたため、オフラインの理由が「disconnected」としか出なかった。最後の1行を保持して `MachineInfo` の `error` に入れる。
- `MachineInfo` の `label` を `name` にしたので、daemonのプロトコルのバージョンを4に上げた。

## 71. boardからのdaemonの再起動の結果を出す

- boardの `daemon.restart` は自分の接続に `Shutdown` を流すだけで結果を待たず、プロトコルの違うdaemonにつながらないときは要求が黙って捨てられ、成功したのか分からなかった。`cq daemon restart` の停止を待ち、止まらなければPIDと理由を付けて失敗する処理をcq-clientの `stop_daemon` に移し、CLIとboardの両方から使う。boardは再起動が終わってから成功か失敗をトーストで出す。

## 72. 各マシンが自分のidを持ち、`local` をやめる

- これまでマシンのidは登録した側が決め、リモートのdaemonは自分のセッションを `local` として出していた。daemonは中継のたびに `local` と登録時のidを書き換え、同じマシンが見る側によって別のidになっていた。リモートのセッションが送り元を `local:abcd` と受け取ると、それは受け手自身を指してしまい、返信できなかった。
- 各マシンが初めて使うときに自分でidを作り（セッションと同じ12桁の乱数）、`~/.codequilt/machine_id` に持ち続ける。daemonは自分のセッションに自分のidを付けて出すので、どこから見ても同じidで同じマシンを指し、中継での書き換え（`tag_incoming` / `untag_outgoing`）と `LOCAL_MACHINE` がなくなった。
- **プロトコルはidだけで動かし、名前は人との境界でだけ使う**：名前はそのマシンが相手をどう呼ぶかに過ぎず、マシンごとに違ってよい。手元のマシンにも予約名ではなく普通の名前（`config.toml` の `name`、既定はホスト名）を付ける。登録したマシンの名前は、既定でそのマシンが名乗る名前にした。
- **idの作り方**：登録した側がidを決める案は、マシンをまたぐと一意にならない。sshの接続先をidにする案は、同じマシンに別の名前で届くことがあり、接続先を変えるとidも変わる。
- daemonはどの接続にもまず自分を載せた `MachineList` を送って名乗る。`cq machine add` はこれでidと名前を知り、手元のマシンや登録済みのマシンを断る。relayは接続のたびにidを確かめ、同じ接続先が別のマシンになっていたら（入れ直しなど）オフラインの理由として知らせる。
- boardは一覧の先頭のマシンを手元のマシンとして扱う。保存したペインの配置とピンは `local/…` をキーにしていたので、保存のキーを `cq.tabs.v3`・`cq.pins.v3` に改めた（以前のものは読まない）。CLIでマシン名を省いたときは、手元だけでなく全マシンから探す。
- daemonのプロトコルのバージョンを5に上げた。

## 73. リモートのクライアントに上流を通して他のマシンを見せる

- WSLのワーカーからWindowsのセッションが一覧に出ず、挨拶に返信できなかった。sshはWindowsからWSLへ一方向に張っていて、WSLのdaemonは自分のセッションしか知らないため。
- **張られたsshを逆向きにも使う**：WSLのdaemonは、sshを張ってきたdaemon（上流）を通して、自分が登録していないマシンもクライアントに見せる。上流のrelayは、WSLのクライアントごとに自分のdaemonへ普通のクライアントとして接続を開いて中継する（代理）ので、一覧・`Routed`・起動などに新しい仕組みが要らない。1本のsshの上で `Upstream { conn, inner }` で包んで多重化する。
- **検討した選択肢**：WSLにもWindowsを登録してsshを張り返す案（Windows側にOpenSSHサーバーが要り、マシンが増えると組み合わせの数だけ登録が要る）。届いたメッセージへの返信だけを届いた経路で送り返す案（作りは小さいが、自分から相手を探して話しかけられない）。上流が自分の一覧をまとめてリモートに送り、リモートのdaemonが持っておく案（daemonが状態を持つことになる）。
- **上流が複数あるとき**：boardやCLIがそれぞれrelayを張るので、上流の接続は複数になる。同じ上流の別の接続なので、最も新しいものを使い、切れたら残りから選び直す。
- **上流から受け付ける要求を絞る**：リモートのマシンは手元のセッションを見て動かせるようになる（ユーザー自身が鍵で入れるマシンなので、信頼の範囲は変わらない）。それでもdaemonの停止、フォーカス、コマンドはそのデスクトップのものなので受け付けない。
- 上流のマシンでクライアント（board、CLI、オーケストレーター）が動いていないとsshが張られていないので、その間はリモートから手元は見えない。daemonどうしが常に接続を保つ案は、daemonが状態を持ち、使っていないときもsshを張り続けることになるため採らなかった。
- daemonのプロトコルのバージョンを6に上げた。

## 74. メッセージの送信元の名前は受け取った側が付ける

- `message` の見出し `[from 名前 (machine:id)]` は送る側が文字列にして本文に埋めていた。マシンの名前はマシンごとの呼び方なので、受け取ったマシンでは通じない名前になることがあった（WSLで受け取った見出しにWindowsの `config.toml` の名前が出る）。
- 送る側は `Inject` の `from` にidだけを載せ、受け取ったマシンのdaemonが見出しを付ける。名前はマシン名もセッション名も、まず受け取ったマシンが持っている情報（`config.toml`、自分の `sessions/`）で引き、無ければメッセージが届いた接続を逆にたどって送信元のマシンに `Names` で聞き、それでも分からなければidを出す。
- **検討した選択肢**：上流に聞く案（WindowsがWSLから受け取ったときは、Windowsに上流がなくセッション名が分からない）。送信元のセッション名だけは送る案（セッション名はどこから見ても同じなので実害はないが、名前を送らないという原則の例外になる）。relayが受け取ったセッションの一覧を接続の間だけ覚えて引く案（送信元に聞けば一覧を覚えずに済む）。
- メッセージを送らない `cq inject`、オーケストレーターへの配達、起動時の最初の指示は `from` を持たず、見出しも付かない。CodeQuiltの外から送ったものは、送る側で `[from outside CodeQuilt]` を付ける。
- 見出しは1行にして本文は次の行から始める。名前の無いセッションは `[from マシン名:セッションid]` とし、idを二度書かない。
- daemonのプロトコルのバージョンを7に上げた。

## 75. プロトコルの違うdaemonにはつなぎ直さない

- daemonを新しいバージョンに入れ替えた後も古いcourierが動き続け、1秒ごとにつなぎ直しては断られて、daemonのログが数分で数十MBになった。
- `DaemonClient::open` はhelloへの最初の返事を待ち、プロトコルの違いで断られたら `Incompatible` を返す。`reconnect`（courier）と `cq mcp` のつなぎ直しはこれを受けたら諦める。courierは終了し、`cq mcp` のツールはdaemonにつながらない旨を返す。
- **検討した選択肢**：間隔を延ばしながらつなぎ直し続ける案（daemonを古いバージョンに戻せば通るが、そうする場面はなく、ログは増え続ける）。daemonが同じクライアントからの接続を記録に残さない案（原因は止まらないクライアントの側にある）。
- boardは画面にdaemonにつながらない理由を出し、`daemon.restart` で入れ替えられるので、今までどおりつなぎ直し続ける。

## 76. ピン留めをやめる

- 左サイドバーのPinned（`ui.toml` の `pinned` と、行のピンのボタンで選んだセッションを上部にも出す欄）を廃止した。実際にはTabsを見ることが多く、Pinnedを見る機会は少なかった。行のピンのボタン、`session.pin`、`ui.toml` の `pinned`（既定の `["orchestrator"]` を含む）、ピンの選択の保存もあわせて消した。
- 既存の `ui.toml` に残った `pinned` は読まれないだけで、害はない。

## 77. トークンの集計をやめ、右サイドバーをLimitsとApprovalsにする

- 右サイドバーのTokens（マシン・ディレクトリ・エージェントごとのトークン）は、出す情報が多いわりに、エージェントのログから数え直した推計で正確さに欠けた。ユーザーが気にするのはほとんどレート制限（Limits）だけだった。
- 表示だけでなく集計の仕組みごとやめた。表示だけ消すと、誰も見ない数字をcq hostが数えて保存し続けることになる。cq hostはClaudeのトランスクリプトを読まなくなり、`tokens` イベント、`sessions/<id>.json` の `tokens_by_hour`、セッション詳細の `tokens:`、`cq usage` のトークンの列も消した。Codexのrolloutは、レート制限・モデル・コンテキスト使用率を得るために引き続き読む。
- 右サイドバーは、よく見るLimitsを上、Approvalsを下にした。
- 既存の `sessions/<id>.json` に残った `tokens_by_hour` は読まれないだけで、害はない。

## 78. リモートのオーケストレーターは専用の仕組みを作らず、マシンをまたいだ報告のループを防ぐ

- リモートマシンでオーケストレーターを動かしたいときは、そのマシンで `cq orchestrator start` すればよい（courierも設定もそのマシンに置かれ、デスクトップを閉じても仲介が続く）。デスクトップのboardからは、上流の中継でリモートのオーケストレーターやセッションと対話できる。そのため、boardやCLIから別のマシンでオーケストレーターを起動する仕組みと、それに要る「別のマシンのプラグインのコマンドを実行する」仕組みは作らない（未実装の項目から外した）。
- **検討した選択肢**：起動の要求（`InvokeCommand`）をそのマシンのdaemonへ転送し、オーケストレーター一式をリモートで動かす案（増えるのはsshせずに起動できることだけで、頻繁に起動するものでもない）。courierはデスクトップに置き、オーケストレーターのセッションだけをリモートで動かす案（デスクトップが止まると仲介も止まり、courierの「自分のマシン」の前提を崩す特別扱いが増える）。
- ただし、オーケストレーターかどうかを、そのマシンのdaemonに登録されたcourierのコマンド（`orchestrator:NAME`）で判定していたため、コマンドの届かない別のマシンのオーケストレーターは報告していた。2台にそれぞれ全マシン担当のオーケストレーターを置くと、互いのターン終了を報告し合い続ける。
- セッションに印を持たせた。`SessionMeta` の `orchestrator` をcq hostが保存し、courierはどのマシンのセッションでもこれで判定する。起動要求の `no_mcp` は使っていたのがオーケストレーターだけだったので `orchestrator` に置き換え、オーケストレーターにはワーカー用のMCPを入れない。`cq claude/codex` には `--cq-orchestrator` を足した（`--cq-no-mcp` は残す）。再開したセッションは印を引き継ぐ。
- **検討した選択肢**：courierのコマンドを他のマシンにも中継する案（コマンドはそのデスクトップのものという方針を崩す）。`scope` が重ならないよう設定する運用で避ける案（既定の全マシン担当のままでループする）。
- daemonのプロトコルのバージョンを8に上げた。印の無い（更新前に起動した）オーケストレーターは、起動し直すまで報告される。

## 79. `scope` は報告の範囲だけにし、設定は `cq orchestrator set` で変える

- `scope` はcourierの報告の範囲だけでなく、オーケストレーターのMCP（`cq mcp --scope`）にも渡り、担当外のマシンのセッションは見ることも話しかけることもできなかった。マシンごとにオーケストレーターを置くと、WSLのオーケストレーターからWindowsのセッションが一切見えない。
- `scope` は報告するマシンだけを絞り、オーケストレーターのツールは全マシンを扱うようにした。`cq mcp --scope` は使う場所がなくなったので消し、`Scope` はcq-clientからcq-orchestratorに移した。
- 設定を変えるのは `NAME.toml` を書き換えて起動し直すしかなかった。`cq orchestrator set [NAME] KEY=VALUE…` で保存し（`toml_edit` でコメントを保つ。値の読み方は `start` の上書きと同じで、空の値は既定に戻す）、courierが使うキー（`scope`、`wake_on`、`batch_seconds`）は動いているcourierにその場で渡す。courierが登録しているコマンド `orchestrator:NAME` の呼び出しで渡すので、新しい通信の仕組みは要らない。設定のパスを出すだけだった `cq orchestrator config` は、パスと中身を出す `cq orchestrator show` にした。パレットには `orchestrator.set` を足した。
- コマンドの形は、`cq machine set` にそろえて動詞のサブコマンド（`show` / `set`）にした。`KEY=VALUE` の書き方は `start` にそろえ、`start` はその起動だけ、`set` は保存、という対にした。
- リモートのオーケストレーターの設定はパレットからは変えられない（パレットのコマンドはboardのマシンで動く）。オーケストレーターには人格の後に自分の名前と `cq orchestrator set` の使い方を伝え、会話で頼めば自分のマシンで実行できるようにした。
- **検討した選択肢**：MCPに `set_scope` ツールを足す案（ツールとcourierへの伝え方が増える。実体はサブコマンドにして、オーケストレーターはそれを実行すればよい）。`scope` 専用のサブコマンド（`cq orchestrator scope --set wsl,pc`）の案（打ちやすいが、キーごとにコマンドが増える）。`cq orchestrator config` を広げて `KEY=VALUE` を保存し、`cq machine` も `config` にそろえる案（`machine` の `add` / `remove` / `list` と動詞・名詞が混ざる）。変更を保存せずその起動の間だけにする案（ユーザーは保存を望んだ）。パレットの `orchestrator.start` に `scope` の欄を足す案（起動後に `set` で変えられる）。

## 80. `share_file` をやめ、返答で言及されたファイルと図・数式のブロックを自動で並べる

- 目的は、TUIでは描画できず、描画しないと意味が大きく失われるもの（画像、図、数式など）を、ダッシュボードで代わりに見せること。ターンが終わるたびに、cq hostがStopの `last_assistant_message` から、描画できる拡張子（画像、PDF、HTML、Markdown）の言及されたファイルと、` ```mermaid ` ・` ```math ` ・`$$ … $$` のブロックを拾い、`files` に足す。同じパスは古いものを消して末尾に足す。拾い方の詳細は `design.md` の「返答で見せるファイル」。
- **`share_file` を廃止した理由**：自動で拾えば、エージェントが見せたいファイルは返答にパスか名前を書くだけで並ぶ。明示的な共有と自動の2つの入口を持つ理由がなくなった。オーケストレーターもフック付きのセッションなので同じ仕組みで拾える。失ったのは、ターンの途中での共有と、ファイルの説明（`caption`）。`ShareFile` を消したので、daemonのプロトコルのバージョンを9に上げた。共有のたびのトーストも、ほぼ毎ターン出てうるさいのでやめた。
- **拾う範囲を設定にしない理由**：Markdownは毎ターンのように言及されて散らかる懸念があったが、同じパスは1件にまとめて末尾に出し直すので、一覧が膨らまない。範囲を絞る設定は、使う場面がはっきりするまで持たない。
- **ファイル名だけでも探す**：Claudeのトランスクリプト73件では、返答でのファイルへの言及の約9割がディレクトリの無いファイル名だった。作業ディレクトリの下を `.gitignore` に従って探し、同名が複数あれば最も新しく更新されたものを選ぶ（エージェントが話すのは直前に触ったファイルであることが多い）。重複はフルパスで判定するので、別の場所の同名のファイルは別々に並ぶ。カーソルを置くとフルパスが出るので、意図したファイルかを確かめられる。
- **図と数式はブロックの中身だけをファイルにする**：返答全体をMarkdownにする案は、図や式の前後の説明が付く代わりに、縮小表示が返答の冒頭になって何の図か分からない。ブロック単位なら図と式でルールが1つにそろう。文中の `$…$` はシェルの変数や金額と区別がつかないので拾わない。ClaudeはふつうMarkdownの `$$` で式を書くので、` ```math ` だけでなく `$$ … $$` も拾う。
- **描画**：mermaidはボードのページでSVGにしてからMarkdownに埋め込み、数式はKaTeXのMathML出力にした。Markdownのiframeはスクリプトを許さないままにでき、MathMLはKaTeXのCSSとフォント（sandboxのiframeからは読み込めない）も要らない。
- **検討した選択肢**：エージェントの機能をSDKやapp-serverで動かし、boardが会話を自前で描く案（図や画像を自由に差し込めるが、承認・ダイアログ・スラッシュコマンドをClaudeとCodexの両方で作り直すことになり、Remote Controlも使えなくなる。Claudeは第三者のアプリでのサブスクリプション認証にも制限がある）。端末の行に図を差し込む案（TUIは画面の状態を覚えて差分で描き直すので、行がずれると表示が壊れる）。表示済みのコードの行に図を重ねる案（全体の描き直しで位置が消え、図の高さもコードの行数に縛られる）。トランスクリプトから画像を拾う案（Claudeのトランスクリプトの形式は内部仕様で変わりうる。ユーザーが貼った画像はユーザーの手元にある）。エージェントが触ったファイルをPostToolUseフックで集めて名前を解決する案（正確だが、ツールのたびにフックが走り、スクリプトで作った画像は拾えない）。ユーザーの発言で言及されたファイルも拾う案（ユーザーは知っているファイルなので要らない）。
